# Сравнение производительности

[English](performance.md) | Русский

Здесь приведены размеры файлов для профилей Go и сквозное сравнение с оригинальной версией Python `gopro-overlay`. Данные и XML-шаблон общего набора виджетов находятся в `examples/`.

## Профили экспорта Go

21 октября 2026 года каждый встроенный профиль CLI отрендерил один и тот же синтетический трейловый GPX длительностью 179,9 секунды с `layouts/virb-run.xml`, размером 1920×1080, частотой 10 кадров/с и восемью воркерами на M4 Pro. CLI записал 1799 кадров. FPS — скорость экспорта; воспроизведение видео остаётся 10 кадров/с. Размер на час линейно рассчитан по фактическому размеру образца в десятичных МБ/ГБ.

Этот замер профилей сделан до исправления подсчёта кадров и пропускает конечный отсчёт. Текущая версия CLI записывает для этой активности 1800 кадров.

| Профиль и результат | FPS экспорта | Размер образца | Оценка размера за час видео |
|---|---:|---:|---:|
| `alpha-prores` — прозрачный ProRes 4444 MOV | 109,8 | 399,6 МБ | 8,00 ГБ |
| `alpha-hevc` — прозрачный HEVC MOV, качество альфа-канала 0.8 | 178,6 | 13,2 МБ | 265 МБ |
| `alpha-vp9` — прозрачный VP9 WebM, CRF 32 и настройки для скорости | 282,7 | 3,6 МБ | 71 МБ |
| `black-h264` — непрозрачный H.264 MP4 на чёрном фоне | 705,9 | 1,0 МБ | 20 МБ |

Размер H.264 относится к отдельному оверлею на чёрном фоне; при композитинге в файл также входит исходное видео. Образец VP9 CRF 28 с пользовательским профилем занимал 2,7 МиБ за тот же интервал, около 56 МБ на час видео; скорость экспорта для него не измерялась.

## Чёрный H.264: оригинальный Python и Go

Для одной и той же трейловой GPX-активности длительностью 179,91 секунды оба варианта создали по 1800 кадров в 1920×1080 при 10 кадрах/с с `libx264`, `veryfast` и `yuv420p`. Python — исходный результат двух запусков. Каждый лимит воркеров Go проверен дважды на M4 Pro; `ffprobe` подтвердил по 1800 кадров и длительность 180 секунд.

Python был взят из upstream-коммита `8e26ee5b452c6aefa38aa6d08557f15139b61e6c` и запущен на Python 3.14.5. Кадры он рисовал последовательно в одном процессе; FFmpeg запускался отдельно и использовал собственные потоки кодировщика.

| Рендерер | Полное время / FPS экспорта | CPU приложения (средние ядра; CPU-с) | CPU FFmpeg (средние ядра; CPU-с) | Пиковый RSS приложения | Пиковый RSS FFmpeg |
|---|---:|---:|---:|---:|---:|
| Оригинальный upstream Python 0.134.0, последовательно | 6,37 с / 283 FPS | 0,74 / 4,72 | 2,27 / 14,44 | 119 МиБ | 578 МиБ |
| Go CLI, 2 воркера | 2,81 с / 690 FPS | 1,45 / 4,09 | 3,97 / 11,16 | 212 МиБ | 504 МиБ |
| Go CLI, 8 воркеров | 2,56 с / 735 FPS | 1,58 / 4,04 | 4,25 / 10,88 | 592 МиБ | 502 МиБ |

Среднее число ядер — CPU-время конкретного процесса, делённое на общее время команды; CPU-с — полное CPU-время процесса. Пиковый RSS — среднее максимальных значений из двух запусков. При двух воркерах пиковый RSS приложения Go на 64% ниже, чем при восьми, а скорость экспорта ниже примерно на 6%. В чёрном режиме число воркеров задаётся вручную; адаптивное окно пока действует в прозрачном режиме. Go передаёт из воркеров YUV420P, Python — RGBA и оставляет конвертацию FFmpeg. Оригинальный Python не поддерживает трейловую метрику `pace`, поэтому в общей копии `layouts/virb-run.xml` для обоих запусков в этом виджете использовалась `speed`. Полное время включает запуск и закрытие FFmpeg; FPS напрямую не сравним с показателем CLI в таблице профилей выше.

## Итоговая скорость Go и Python: прозрачный ProRes 4444

Оба экспортёра создали по 1800 кадров для одинаковых синтетических активностей длительностью 3 минуты, размером 1920×1080 и частотой 10 кадров/с, используя прозрачный ProRes 4444 на M4 Pro. В текущих запусках Go использовал четыре воркера и адаптивное окно в 4–16 кадров; оригинальный Python обрабатывал кадры последовательно в одном процессе. FFmpeg мог использовать собственные потоки. Время и показатели процессов — средние двух запусков.

| Активность | Рендерер | Полное время / FPS | CPU приложения (средние ядра; CPU-с) | CPU FFmpeg (средние ядра; CPU-с) | Пиковый RSS приложения | Пиковый RSS FFmpeg |
|---|---|---:|---:|---:|---:|---:|
| Обычная | Go, 4 воркера (адаптивное окно) | 15,02 с / 121,7 FPS | 0,54 / 8,16 | 9,28 / 139,38 | 194 МиБ | 968 МиБ |
| Обычная | Python, последовательно | 15,81 с / 113,9 FPS | 0,42 / 6,71 | 9,38 / 148,38 | 120 МиБ | 971 МиБ |
| Трейловая | Go, 4 воркера (адаптивное окно) | 14,86 с / 122,7 FPS | 0,54 / 8,06 | 9,36 / 139,11 | 194 МиБ | 868 МиБ |
| Трейловая | Python, последовательно | 15,87 с / 113,4 FPS | 0,42 / 6,69 | 9,32 / 147,98 | 119 МиБ | 884 МиБ |

Средние ядра — CPU-время процесса, делённое на полное время команды. RSS — среднее пикового resident memory процесса по двум запускам, измеренного отдельно для приложения и FFmpeg; эти значения не следует складывать, так как процессы могут использовать общие страницы памяти. FPS включает запуск и закрытие FFmpeg, поэтому его нельзя напрямую сравнивать с показателем CLI в таблице профилей выше.

В прозрачном режиме FFmpeg занимает около 9,3 ядра, а процесс Go/Python — около 0,5. Это указывает на ограничение кодировщиком FFmpeg и обратным давлением через его входной pipe: рендереры большую часть времени ждут, пока FFmpeg примет и закодирует кадры. Это вывод по загрузке процессов, а не прямое измерение времени блокировки `write`. При текущем адаптивном окне пиковый RSS Go — около 194 МиБ при скорости 122 FPS. У Go всё ещё выше RSS и CPU-время приложения, чем у Python; основную нагрузку CPU несёт FFmpeg. Замер чёрного режима выше также показывает, что уменьшение числа воркеров снижает RSS приложения, с небольшой потерей скорости.

Кадр метрик на отметке 90 секунд выглядел близко у HEVC и VP9 после композитинга на серый фон; полное сравнение движения не проводилось. При декодировании через `libvpx-vp9` альфа-канал VP9 содержал значения от 0 до 255, но стандартный декодер VP9 на этом компьютере альфа-канал не показывал. HEVC Alpha декодировался через AVFoundation со значениями альфа-канала от 0 до 255. VP9/WebM поддерживает альфа-канал в совместимых декодерах; приложение для монтажа также должно поддерживать прозрачность WebM.

### Условия замера

- Компьютер: Apple M4 Pro, 24 ГБ RAM, macOS 27.0; FFmpeg 8.0.
- Go 1.26.5. Python: upstream `gopro-overlay` 0.134.0, коммит `8e26ee5b452c6aefa38aa6d08557f15139b61e6c`, Python 3.14.5.
- Go CLI вызывает `metrics.Process` перед подготовкой виджетов, включая стандартные короткое, длинное и очень длинное окна.
- В сравнении прозрачного режима используется `examples/performance.xml`, одинаковый шрифт Arial, размер 1920×1080, частота 10 кадров/с и ProRes 4444 (`prores_ks`, профиль 4, `yuva444p10le`, 16 бит альфа); Go использует четыре воркера и адаптивное окно 4–16 кадров, Python рендерит последовательно. Профиль Python добавляет `-r 10` после значения по умолчанию `-r 30`.
- В сравнении чёрного режима используется общий вариант `layouts/virb-run.xml`, `libx264`/`veryfast` и `yuv420p`; неподдерживаемый Python виджет `pace` заменён на `speed` в общем шаблоне.
- `examples/benchmark-normal.gpx` и `examples/benchmark-slow-trail.gpx` — синтетические активности на 181 точку длительностью 179,91 секунды. Обычный профиль имеет среднюю скорость 3,4 м/с и набор высоты 9 м; трейловый — 1,4 м/с и 30 м. В обоих есть скорость, пульс, каденс и мощность. Личные данные и сетевые карты не используются.
- Каждая активность и рендерер запускались по два раза. Для Go в чёрном режиме проверялись два и восемь воркеров, в прозрачном — четыре. В прозрачных тестах порядок чередовался; в чёрных сначала запускался Go, затем Python. Файловый кэш ОС не очищался.
- CPU-время и RSS отдельных процессов снимались командой macOS `ps -Ao pid=,ppid=,time=,rss=,comm=` каждые 200 мс. Среднее число ядер — CPU-время процесса, делённое на полное время команды; пиковый RSS — среднее максимальных значений двух запусков.

Также проверялся исходный `layouts/virb-bike.xml`, но он не использовался в таблице производительности: Python рисует весь профиль активности на графике, а Go — историю только до текущего кадра. Общий шаблон позволяет сравнить работу виджетов, но не доказывает полного визуального совпадения.

### Подробные результаты Go и Python

Все четыре прозрачных файла проверены через `ffprobe`: по 1800 кадров, 180 секунд, 1920×1080, 10 кадров/с, ProRes 4444 (`yuva444p12le`). Таблицы выше показывают среднее двух запусков для каждой активности и рендерера.

### Повторение замеров

Сначала соберите Go, чтобы компиляция не вошла во время замеров:

```sh
mkdir -p tmp
go build -o tmp/video-overlay-cli ./cmd/video-overlay-cli
```

Укажите в `GOPRO_OVERLAY_DIR` путь к оригинальной upstream-копии на коммите `8e26ee5b452c6aefa38aa6d08557f15139b61e6c` и установите её во временное окружение:

```sh
export GOPRO_OVERLAY_DIR=../gopro-dashboard-overlay
python3.14 -m venv tmp/gopro-overlay-bench
tmp/gopro-overlay-bench/bin/pip install -e "$GOPRO_OVERLAY_DIR"
mkdir -p tmp/gopro-overlay-bench/config tmp/gopro-overlay-bench/cache
```

Укажите `BENCH_FONT` как путь к установленному файлу Arial, чтобы оба рендерера использовали один шрифт.

Создайте файл `tmp/gopro-overlay-bench/config/ffmpeg-profiles.json`:

```json
{
  "bench-alpha": {
    "input": [],
    "output": ["-vcodec", "prores_ks", "-profile:v", "4", "-pix_fmt", "yuva444p10le", "-alpha_bits", "16", "-r", "10"]
  }
}
```

Запустите каждую активность обоими способами; для второго профиля замените `normal` на `slow-trail`. Python оставьте на последовательном режиме по умолчанию; для Go задайте восемь воркеров:

```sh
/usr/bin/time -lp tmp/video-overlay-cli render \
  --activity examples/benchmark-normal.gpx --layout examples/performance.xml \
  --output tmp/go-normal.mov --size 1920x1080 --fps 10 --workers 4 \
  --font "$BENCH_FONT" \
  --background transparent --profile alpha-prores

/usr/bin/time -lp tmp/gopro-overlay-bench/bin/gopro-dashboard.py \
  --use-gpx-only --gpx examples/benchmark-normal.gpx \
  --layout xml --layout-xml examples/performance.xml \
  --profile bench-alpha --config-dir tmp/gopro-overlay-bench/config \
  --cache-dir tmp/gopro-overlay-bench/cache --overlay-size 1920x1080 \
  --bg 0,0,0,0 --font "$BENCH_FONT" \
  tmp/python-normal.mov
```

`/usr/bin/time -lp` показывает суммарные показатели команды; разделение приложения и FFmpeg в таблицах выше получено отдельным опросом `ps` для каждого PID.

В Python есть параметры `--print-timings` и `--profiler`. Go CLI выводит общее время рендера и средний FPS; переменная `OVERLAY_STAGE_TIMING=1` включает длительность загрузки активности, ресэмплинга, подготовки метрик и рендерера, разбора XML, запуска FFmpeg, передачи кадров и закрытия FFmpeg. Этап передачи кадров включает отрисовку и конвертацию в Go, а также запись в FFmpeg, поэтому его длительность нельзя отдельно отнести к Go или FFmpeg. Профиль CPU Go показал, что значительная часть времени уходила на повторную растеризацию текста с обводкой. Сейчас текстовые спрайты разделяются между воркерами, а геометрия глифов с обводкой переиспользуется. В отдельном запуске с тестовым приёмником FFmpeg отрисовка 1800 кадров велосипедного шаблона сократилась с 10,46 до 4,25 секунды. Этот прогон исключал кодирование видео и не входит в таблицу общего времени.

### Ограничения

- Файлы активности синтетические и длятся три минуты. Окно метрик 120 секунд проверяется, но масштабирование на более длинные маршруты не измерялось.
- Сравнивается только `gopro-overlay`. Полное совпадение Go со всеми шаблонами не проверялось.
- Файловый кэш ОС не очищался, поэтому это не замер с холодным кэшем. Опрос процессов каждые 200 мс может пропустить кратковременные пики RSS и слегка повлиять на время.
- Этапный вывод Go разделяет загрузку и подготовку, но не разделяет отрисовку, конвертацию, запись через pipe и кодирование FFmpeg.
